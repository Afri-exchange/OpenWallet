Spendkit · sandbox demo

Give your AI agent
a card it can't overspend.

A developer ships a shopping agent. Their users verify once, fund a card, and stay in control of what the agent can buy.

The problem

Agents need to pay. Nobody wants to hand over a card.

  • Sharing your own card with an agent means unlimited exposure.
  • An agent can't pass KYC, so it can't hold a card itself.
  • Developers don't want to build identity checks, wallets and spend controls from scratch.
How it works

One person, one verified card, many limited agents.

Developercreates users and agents from their serverdk_ key · /developer/v1
→
Userpasses KYC once, funds the card, sets limitshosted /connect page
→
Agentpays within its budgetak_ token · MCP or REST

The agent never sees card details and never does KYC. The user's money is split into per-agent sub-balances.

Step 1 · Developer

Create a user and send them to the hosted page.

POST /developer/v1/users            {"externalId":"guest-1","email":"..."}
POST /developer/v1/users/:id/sessions
→ https://…/connect#session=us_…

The session lives in the URL fragment, so it never reaches a server log. Nothing to build for KYC or spend controls.

Step 2 · User

Verify once. Get a real Visa card.

  • KYC runs through Miden. Approval issues a Visa card and a USDC deposit address.
  • Send USDC to that address and it is credited and moved onto the card.
  • The developer is told by signed webhooks: kyc.updated, card.issued, funding.completed.
Step 3 · Agent

Create the shopping agent, with limits.

POST /developer/v1/users/:id/agents
{"name":"shopper","perTransactionCents":2000,
 "dailyCents":10000,"allowedMccs":["5734","5815"]}
→ {"agentId":"a_…","token":"ak_…"}

POST …/agents/:id/fund   {"amountCents":5000}

$20 per payment, $100 a day, software and digital goods only.

The limits hold.

$1.50 over the per-payment limit      declined  per-transaction limit exceeded
$1.00 at a retail category            declined  merchant category not allowed
limit above the card's tier           refused   server says which limit
$1.00 at an allowed category          approved
same idempotency key again            approved  first result; no double charge
revoke the agent → old token          401
Optional

Privacy mode: a fresh card per payment.

  • Every payment uses a one-time card for exactly that amount.
  • A merchant never sees a card number that works twice, and purchases can't be linked.
  • Limits, balances and idempotency behave the same. If a card can't be made, nothing is charged.
Be upfront

What this is today.

  • Sandbox only. The service refuses to start against a non-sandbox Miden URL. No real money moves.
  • The demo uses a dummy identity and a simulated USDC deposit as shortcuts. Real users do both on /connect.
  • Privacy mode is capped by Miden at 3 cards per customer in the sandbox.
  • Not production-ready yet; see docs/production-gaps.md.
